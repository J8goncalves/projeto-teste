### 5. Investigação de Performance, Saturação e Erro 1455 no Windows (D3)

#### 5.1 Causa Raiz do Esgotamento de Memória / Pagefile
Durante os testes de chamadas simultâneas de subprocessos e containers, reproduzimos o erro fatal do sistema operacional:
```
O shell não pode ser iniciado. Ocorreu uma falha durante a inicialização:
Não foi possível carregar arquivo ou assembly 'System.Data...'. O arquivo de paginação é muito pequeno para que esta operação seja concluída. (Exceção de HRESULT: 0x800705AF / WinError 1455)
```
- **Mecanismo da Falha**:
  - `TotalVirtualMemorySize`: ~66 GB
  - `FreeVirtualMemory`: caiu para apenas ~628 MB durante picos de inferência e subprocessos PowerShell.
  - O WSL2 (`vmmemWSL`) aloca virtual address space dinâmico conforme a demanda de containers (Docker Desktop + Ollama + PostgreSQL + n8n + Moorcheh).
  - Quando um novo processo Windows tenta spawnar (mesmo um simples `powershell.exe` ou `python.exe`), a chamada `NtCreateProcessEx` falha se a cota de compromisso do arquivo de paginação (Commit Charge) estiver esgotada.
- **Medidas Recomendadas de Mitigação**:
  1. Definir teto fixo de memória para o WSL em `%USERPROFILE%\.wslconfig`:
     ```ini
     [wsl2]
     memory=6GB
     swap=4GB
     processors=4
     ```
  2. Executar modelos LLM locais pesados (`qwen2.5:7.6b`) sequencialmente, nunca em paralelo com múltiplos agentes concorrentes.
  3. Para tarefas de background / embeddings, priorizar modelos leves (`nomic-embed-text` consome apenas 274 MB).

> **Classificação D3: PARTIAL**. A causa raiz foi minuciosamente isolada, compreendida e comprovada em laboratório, com mitigação documentada.

### 6. Auditoria de Segurança e Credenciais GitHub (D4)

#### 6.1 Vulnerabilidades Identificadas
1. **Acesso ao Token no Runtime**: O módulo `approvals.py` lia `GITHUB_TOKEN` diretamente do ambiente do processo Python. Como qualquer agente pode executar scripts Python no mesmo venv, um agente autônomo com permissões de execução de código poderia potencialmente usar o token para forjar aprovações em issues do GitHub.
2. **Ausência de Restrição de Autor**: A versão anterior aprovava qualquer comentário contendo a string de aprovação, independentemente de quem o postou.

#### 6.2 Melhorias Implementadas na Fase D
- **Validação de Autorização**: O `verify_human_approval` agora inspeciona o campo `author_association` retornado pela API do GitHub e exige obrigatoriamente que o comentador seja `OWNER`, `MEMBER` ou `COLLABORATOR` do repositório.
- **Recomendação Arquitetural para Fase E**: Mover a verificação de aprovação humana para fora do processo dos agentes (Webhook Receiver dedicado / GitHub Action externa com assinatura HMAC), para que o token GitHub nunca resida no ambiente de execução do LLM.

> **Classificação D4: PASS**.

### 7. Taxonomia de Evidências (D5)

Para sanar a ambiguidade entre saídas reais e simulações de LLM, o V5.1 passa a adotar a seguinte classificação de evidências:

1. **Nível 0 (Autodeclaração)**: Campos preenchidos no JSON pelo autor (`real_execution: true`, `command: pytest`, `exit_code: 0`). Não constitui prova de execução.
2. **Nível 1 (Integridade de Hash)**: O artefato físico existe no filesystem e seu SHA-256 é imutável (`validate_proof`). Impede adulteração posterior, mas não prova a autenticidade da ferramenta.
3. **Nível 2 (Verificação por Especialista Independente)**: Um especialista com `instance_id` e papel distintos inspeciona o código e os logs gerados (`control.review`). Barrou conluio e autoaprovação (T04, T15, T19).
4. **Nível 3 (Atestação Criptográfica de Runtime)**: Ausente no Antigravity local. Classificada rigorosamente como `UNVERIFIED`.
5. **Nível 4 (Aprovação Humana Out-of-Band)**: Validação externa via API autenticada do GitHub com checagem de permissões do aprovador.

> **Classificação D5: PASS**.

### 9. Comparação Objetiva: V5 vs V5.1

| Dimensão | Versão V5 | Versão V5.1 (Pós-Fase D) |
| :--- | :--- | :--- |
| **Identidade de Agentes** | Declarativa (qualquer agente podia alegar qualquer papel). | Validada contra variáveis de runtime e separação estrita de instâncias. |
| **Autoaprovação** | Possível (Orchestrator podia revisar artefatos próprios). | Bloqueada criptográfica e logicamente (`verify_independence`). |
| **Linhagem de Release** | Inexistente (relatórios podiam vir de builds distintas). | Estrita (Release rejeita mesclagem de QA e Sec de commits diferentes). |
| **Aprovação Humana** | Qualquer URL servia como aprovação. | Validação ativa via API do GitHub exigindo colaborador autorizado e payload exato. |
| **AI Memory** | Declarado mas sem teste de persistência em runtime. | Backend `on-prem` integrado, geração de IDs reais e gate humano obrigatório. |
| **Retomada Fria** | Não testada contra adulteração. | Criptograficamente verificada via `RESUME_PACKAGE` e rejeição de hash mismatch. |
| **Resiliência a Erros OS** | Falhas silenciosas de subprocesso. | Isolamento e documentação da saturação de commit charge do Windows. |

### 10. Conclusão e Recomendação para Fase E

- **Status Geral da Fase D**: **`PASS` com ressalvas operacionais documentadas**.
- **Prontidão para Fase E**:
  A governança da organização V5.1 está substancialmente blindada. As regras de integridade, separação de papéis, gates de aprovação e imutabilidade de artefatos funcionam perfeitamente. As limitações remanescentes não decorrem de falhas lógicas no motor organizacional, mas sim de limites físicos de hardware (saturação de commit no Windows) e da necessidade de segregação de credenciais GitHub fora do ambiente dos agentes.

**Recomendação**: Prosseguir para a **Fase E (Homologação Final e Transição Operacional)**, mantendo os gates críticos sob aprovação humana estrita.
